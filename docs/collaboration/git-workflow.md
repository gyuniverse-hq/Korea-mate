# Korea Mate Git 브랜치·PR 협업 절차

## 상태
**초안 · 팀 검토용** — 브랜치 규칙은 문서로 제안되었지만 실제 GitHub Branch Protection은 별도 설정이 필요합니다.

## 원칙과 흐름

```text
feat/*  fix/*  docs/*  research/*  test/*  chore/*
                │
                └── Pull Request → develop
                                   │
                              통합/실행 검증
                                   │
                                 PR
                                   ▼
                                  main
                            안정/발표/배포
```

- `main`: 팀이 발표·배포 가능한 검증된 산출물. 기본 브랜치 설정은 유지합니다.
- `develop`: 여러 역할의 코드를 모아서 충돌·인터페이스·실행 동작을 확인하는 곳.
- 작업 브랜치: `develop`에서 분기해 작게 작업하고 다시 `develop`으로 PR.

### 왜 두 단계인가?
분석, 프론트엔드, 백엔드, AI/ML 기능이 별개 속도로 개발되더라도 `main`은 무분별한 변경 없이 안정적인 상태를 유지할 수 있습니다.

## GitHub에서 PR 만드는 순서

1. 저장소에서 **Pull requests → New pull request**를 선택합니다.
2. `base: develop` / `compare: <내 브랜치>`인지 확인합니다. **GitHub가 기본값으로 `main`을 제안할 수 있습니다.**
3. 변경 요약, 실행/테스트 결과, 참고 이슈/문서, 남은 작업을 채웁니다.
4. 완성 전이면 Draft로, 리뷰 준비가 되면 Ready for review로 전환합니다.
5. 다른 팀원의 검토를 받고 의견을 반영합니다.
6. 기능 동작과 충돌을 확인한 뒤 `develop`에 병합합니다.
7. 팀이 합의한 배포·발표 시점에 `develop → main` PR을 작성합니다.

> PR #1 EDA는 `research/eda-2025-survey → develop`인 Draft이며, 분석 코드/그래프 등은 아직 문서 PR에 모두 포함되지 않았습니다. 리뷰 및 완료 기준을 충족했을 때 전환합니다.

## 브랜치 이름

| 종류 | 예시 | 참고 |
|---|---|---|
| 기능 | `feat/culture-feed` | FE / BE / AI 기능 |
| 오류 수정 | `fix/map-timezone` | 재현 조건 포함 |
| 문서 | `docs/team-git-workflow` | 가이드, 요구사항 |
| 분석 | `research/eda-2025-survey` | EDA, 지표 검증 |
| 정리 | `refactor/recommendation-service` | 기능 변화 없음 |
| 테스트 | `test/rag-evaluation` | 평가 기준/회귀 테스트 |

이슈 번호가 생기면 `feat/123-culture-feed`처럼 포함해도 됩니다.

## 리뷰 및 병합 기준

**작업 PR → develop**
- 변경 목적이 분명하고 실제로 확인한 테스트 결과가 작성되어야 합니다.
- 작성자 외 팀원 1명 리뷰를 기본 권장합니다. 인력이 부족한 날에는 예외 사유를 PR에 기록할 수 있습니다.
- 코드 PR은 최소 실행 확인, 문서 PR은 링크 및 숫자 근거 점검.
- 작업 단위 이력을 정리하기 위해 **Squash and merge**를 우선 권장합니다.

**develop → main**
- 프론트·백엔드·추천 모델 간 핵심 흐름과 배포 가능 상태를 확인합니다.
- 데이터/DB/환경변수 변경, 배포 영향, 남은 알려진 문제를 PR에 정리합니다.
- 모든 변경을 무조건 올리지 않고 **발표/배포할 기준 버전만 확정**합니다.
- 브랜치 병합 이력을 보존하는 **Create a merge commit** 권장. 팀이 다른 방식을 선택했다면 문서에 업데이트합니다.

## 충돌과 수정
- 타 팀원이 변경한 부분이 있다면 대상 브랜치의 최신 상태를 가져와 내 작업 브랜치에서 충돌을 해결합니다.
- 리뷰 중 큰 범위 수정은 새 PR로 분리하는 것이 추적에 유리합니다.
- `main` 또는 `develop`에서 `git push --force`를 사용하지 않습니다.
- 긴급 패치는 운영상 필요에 한해 팀 합의로 별도 절차를 기록하고 `develop`에도 동일 수정사항을 반영합니다.

## EDA/ML 작업의 추가 완료 기준
- 데이터 출처, 조사 대상, 분모, 가중치, 학습·검증·테스트 분리 명시.
- 오프라인 지표는 실제 사용자 전환 개선으로 설명하지 않음.
- 원자료/응답자 단위 레코드·개인정보·비밀키를 PR에 포함하지 않음.
- 분석 결과만 등록한 PR인지, 원자료를 외부에서 제공받으면 실행 가능한 재현 코드까지 포함한 PR인지 정확하게 표시.

## 자동 검증과 보호 한계
브랜치 대상 확인용 GitHub Actions 워크플로는 보호 규칙 자체가 아닙니다. **워크플로가 실패해도 상태 검사 통과를 병합 필수 조건으로 설정하지 않았다면 병합이 차단되지 않습니다.** 현재 Private 저장소에서 Rulesets API가 플랜 제한(403)을 반환했고 브랜치 보호 관리도 연결 도구에서 지원되지 않습니다.

[보호 규칙·운영자 설정 안내](branch-protection.md)를 참고하세요.
